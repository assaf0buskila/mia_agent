# Assaf OS: PostgreSQL primary, asynchronous Sheets mirror

Architecture plan, 2026-10-13. Owner direction: OS data first; Sheets can receive a backup copy afterward. Four seconds is an aspirational measured SLO. This authorizes planning only. No production reads/writes, schema migration, credentials, provisioning, deletion, authority change, deployment or new benchmark was performed for this plan. The approved 12-file VM release remains exclusively owned by MIA task `01a13575-4a78-7612-ba73-fa29e83a60e4`; implementation must start from its eventual verified release SHA without editing its worktree or scope.

## Recommended target and infrastructure reuse

Reuse the existing MIA FastAPI VM and PostgreSQL 16 first. Keep the Cloudflare frontend, opaque owner sessions, numeric-owner Telegram boundary, immutable approvals, and existing public CRM. Add a dedicated OS ledger and outbox in the same PostgreSQL instance, with explicit workspace scoping. Do not create another CRM or infer that `crm_contacts` already implements works, receipts, hours and expenses.

Critical path:

`OS or private-owner approval -> MIA -> PostgreSQL atomic commit -> fresh primary receipt/state read -> verified OS result`

Independent asynchronous path:

`committed OS outbox event -> bounded mirror worker -> Sheets upsert -> readback -> mirror watermark`

Google availability no longer blocks an OS commit. Database failure does: never fall back to writing Sheets. “Saved in OS” means primary commit and fresh primary verification; “Sheets mirror pending / synced / delayed / unknown / conflict” is separate. Sheets is an export/recovery aid, not the only backup and not an alternate writer.

Verified source foundations:

- `ops/gcp/vm/compose.yaml`: one PostgreSQL16 container on loopback, data under `/var/lib/mia/postgres`, app and migration containers on the existing VM. The repo documents `e2-small`, 20GB disk and me-west1-a; actual current capacity/headroom and billing were not inspected.
- `app/db/session.py`: SQLAlchemy/psycopg3 engine and session factory; `app/db/migrate.py`: ordered additive `migrations/*.sql`, not Alembic. Its simple semicolon splitter needs review before PostgreSQL functions/complex procedural SQL; do not silently add unsupported migration syntax.
- `app/api/owner_sessions.py`: current numeric-owner/workspace/scope checks, opaque PostgreSQL sessions and mutation Origin/CSRF.
- `app/services/owner_actions.py` and `ApprovalRow`: immutable approval envelope and durable decision/execution tracking. Their external-provider execution path splits provider claim/effect/completion; a local DB write needs its own transaction integration rather than copying that split.
- `CrmOutboxRow`, `app/workers/crm_delivery.py`: dedupe, lease, backoff, unknown reconciliation and telemetry patterns. Reuse patterns, not CRM destinations or its automatic editable-Sheet import. Add an OS-specific mirror worker/outbox.
- `ops/gcp/vm/mia`: `pg_dump -Fc` backup writes to the same host. Documentation also describes daily disk snapshots with seven-day retention; fresh policy/restore evidence remains a later read-only operational check.

## Primary data and transaction contract

Use namespaced additive tables, separate from public CRM. Proposed tables are `os_workspaces/authority`, seven typed domain tables (`os_leads`, `os_clients`, `os_works`, `os_payments`, `os_time_entries`, `os_expenses`, `os_tasks`), `os_proposals`, `os_receipts`, immutable `os_events`, `os_outbox`, `os_mirror_state`, and import/staging/issues tables. Final SQL names are implementation choices.

Every key, reference and lookup includes workspace binding; the authenticated server supplies it. Preserve existing string IDs and revisions, including lead-to-client person identity. Do not regenerate IDs or assume a particular prefix is valid for every imported person. Store money as checked integer minor units, business dates as dates interpreted in Asia/Jerusalem, event times as timezone-aware UTC, and currency explicitly. Port existing Hebrew enum semantics through a canonical mapping; preserve null/missing coverage, separate currency totals, net refunds/cancellations, paid-only expense totals and missing-time hourly nulls. Agreed work amount never becomes receipt income. Derive calculated fields from accepted primary inputs, not imported formatted/formula cells.

Constraints plus transactional domain validation must preserve references, client/work/path consistency, contact duplicate policy, unique expense source semantics, refund original/payment limits, promotion atomicity and immutable paths. Determine exact duplicate keys from the existing `runtime.js` rules; do not invent a new phone/source normalization policy during migration. Start with a short transaction-scoped per-workspace database lock if that is the safest bounded implementation; later narrow locking only if measurements justify it. Google calls never occur while holding this lock.

Proposal creation stores exact canonical before/after input, expected revision, dependency/source fingerprints, numeric owner, workspace, authority epoch, expiry and stable approve/reject IDs. It changes no domain row. Keep the existing ten-minute OS expiry, narrowed to the outer Telegram approval expiry. The model may propose but cannot approve. Both browser and Telegram resolve the same immutable DB proposal/receipt; retain private CRM-source revalidation before promoting a captured prospect.

Approval transaction:

1. Verify current authenticated owner, scopes/policy/kill switch, exact proposal and decision ID, source/authority epoch and expiry. Acquire a consistent ordered lock; recheck target and dependency revisions/fingerprints inside the transaction.
2. Apply all business mutations and affected deterministic aggregates. A lead promotion updates lead and client together. Consume the approval/proposal and insert immutable decision receipt, audit event and deduplicated mirror outbox event **in the same PostgreSQL transaction**. The existing owner approval/execution state for this local operation must participate in that transaction or be a recoverable projection of the primary receipt; it cannot become an independent second success authority.
3. Commit with durable settings verified before activation; do not disable fsync or synchronous commit for speed. After commit, use a fresh primary read in a consistent snapshot to return the receipt and current record/summary at a workspace version at least the receipt's commit version. Bound/paginate large lists; expose matching snapshot/version identifiers so concurrent newer writes cannot make the UI render an older response.
4. If acknowledgement or verification is lost, the exact request stays inconclusive until its primary receipt is read. Query the same request; never mint a replacement decision or fall back to Sheet writes. A known commit with temporarily unavailable verification is reported separately from a fully verified result.

Enforce unique `(workspace, proposal-request-id)`, `(workspace, decision-request-id)`, and one terminal decision/receipt per proposal; request fingerprint mismatch is rejected. Store canonical request digests excluding transport freshness timestamps. Simultaneous browser/Telegram approval commits once; duplicate delivery returns the original receipt. PostgreSQL transaction rollback leaves no half-applied row, receipt or outbox event. Safely retriable pre-commit serialization failures are different from unknown commit outcomes.

Version the transport honestly: current validators require `source=google_sheets`. Introduce a reviewed database-primary contract with `primary_source=postgresql`, authority epoch, primary snapshot/commit version and separately identified mirror workbook/status. Update browser and private-owner readers together. Do not label a database result as Google-sourced to satisfy old validators. Bind recovery storage to authority epoch; old markers and cards require explicit settlement/expiry, not silent relabelling.

## Mirror semantics and retries

An outbox record contains workspace, event ID, commit sequence, affected entity/record/revision, schema/destination binding, status, attempts, next-attempt time, lease owner/generation and sanitized last-error code. It is created transactionally, even while the mirror is offline. A publisher on the existing VM uses bounded batches, jittered backoff and per-workspace serialization; it projects the latest primary version rather than writing an old queued payload over newer data. Coalescing may reduce redundant updates while audit events remain immutable.

Upsert by stable ID and version/hash, not blind append or mutable row number alone. Pin target workbook and exact tabs/columns, check headers, preserve unrelated historical data, and write literal values so customer text cannot become a Sheet formula. Record per-record acknowledgements and advance the workspace watermark only after readback verifies all affected rows/versions in the batch. A queued watermark is not a confirmed mirror.

External delivery is at-least-once with reconciliation, not atomic exactly-once across PostgreSQL and Google. Lost acknowledgement becomes `unknown`; inspect destination ID/version/hash before retrying. A late writer after lease loss can race a later export because Sheets does not consume the DB lease token atomically. Generation checks, one active publisher and readback/repair reduce this risk but must not be sold as a cross-system transaction. Detected stale/tampered/conflicting output stays visible and converges from the current primary; it never rolls back a valid primary commit. Keep retryable and permanent failures distinct; authentication/header/schema conflicts pause that destination for owner review.

Require bounded periodic anti-entropy checks **even when the outbox is empty**. Compare mirror stable IDs, revisions/hashes, epoch, row counts and manifest against current primary versions. A stale leased write can finish after a newer successful readback; an empty queue cannot establish lasting sync. Track `last_verified_at`, verified version and scan coverage; present “last verified” rather than an unqualified permanent “synced.” Repair a proven delayed exporter regression from current primary, and quarantine unexplained owner edits. Test a delayed old request completing after the new readback with no pending outbox events, and require detection plus repair/conflict visibility. Pick a bounded scan interval/budget during the mirror-policy decision; this control is an authority-activation gate.

Suggested initial mirror objective for owner decision: attempt delivery within a minute when Google is healthy, show age/backlog immediately, alert after an agreed lag window. Google outages may delay it longer without losing primary writes. Outbox capacity/retention must be sized to the agreed maximum outage; show degraded mirror health before exhaustion. No tight live lag guarantee is claimed.

## Native Sheet edit policy

Recommend **read-only protected mirror tabs** after cutover. If the owner wants occasional spreadsheet entry, provide a separate draft/inbox workflow: capture edit with its base primary revision, show a precise proposal in OS, and commit only after explicit owner approval and conflict revalidation. Editing the mirror never automatically changes primary data. An owner can override Sheet protections, so detect drift and quarantine it; do not silently overwrite edited financial data or auto-import it.

This is a later product decision, not a permission already granted. Disable/fence old authoritative Apps Script propose/approve and native/scheduled reconciliation writers at the coordinated cutover. Preserve read/audit access and historical journals. Every MIA, browser, CRM-import preparation, legacy Sheet writer and background trigger path must be inventoried; routing only the browser to PostgreSQL leaves a dual-writer hazard.

Prefer a separate protected mirror workbook to isolate old Script triggers and preserve the original workbook as a frozen migration source. Reusing the current workbook is possible only after approved fencing and a full backup, with its historical metadata preserved. Destination creation/sharing, access scopes and any new credentials need separate authorization.

Unaccepted/id-less/raw-changed rows remain staged exceptions until their import/reconciliation treatment is explicitly approved; planning grants no such source write.

## Backup, restore and rollback

Sheets is a lagging projection without the full transaction/proposal/idempotency/outbox ledger, so it cannot be the sole recovery system. Current same-host dumps are insufficient against host loss. Before authority activation require verified encrypted off-host database backups, separate restore access, retention and periodic isolated restore drills. Disk snapshots complement them but do not establish point-in-time application recovery. Choose a DB recovery point objective (RPO) and time objective (RTO); daily dumps imply a potential day of loss, while a tighter RPO needs additional frequent backups or base-backup/WAL archival. PostgreSQL documents SQL dumps, filesystem backups and continuous archiving as separate approaches: [backup and restore](https://www.postgresql.org/docs/16/backup.html).

Proposed discussion targets, not promises: RPO no more than 15 minutes and RTO no more than two hours. Validate the actual storage/backup design and restore duration before accepting them. For the small single-VM option, disclose its one failure domain and absence of demonstrated HA. Preserve OS audit, receipts, proposals, idempotency and mirror checkpoints with data; losing those can duplicate external effects after restore. Restore to an isolated host/database with mirror and all existing CRM/reminder/outbound jobs paused, validate version/checksums and receipt-ledger state, then explicitly resume only reviewed effects. Do not claim an untested scheduled backup is recoverable.

Before promoting a restore, **fence the old primary and all its writers/exporters**, including an old host that might reconnect. Issue a new recovery authority epoch and invalidate or explicitly settle restored pending proposals, Telegram cards and browser markers; do not accept pre-disaster approvals against a recovered older state. Quarantine and reconcile the possible RPO-loss window using verified WAL/backup, exact receipts, source evidence and mirror/export manifests before resuming business writes or external effects. A receipt absent from the restored database does **not** prove the original action never committed. Unresolved loss-window outcomes stay unknown and block their affected operations. These recovery controls are activation gates, not optional follow-ups. The current `mia restore` command drops/recreates the production database and automatically starts services; it is unsuitable unchanged for a safe isolated drill. Prepare a reviewed isolated restore runbook with network/effects disabled rather than invoking that production command.

Before the first primary write, rollback can keep the old Sheet authority after abandoning the inactive import. After primary writes, prefer rolling application code forward or back to a compatible DB-primary release. **Do not switch back to the old Sheet snapshot**: it may lag or omit committed records. A reverse-authority migration requires a new approved maintenance freeze, settled outcomes, export of the complete primary delta including history/revisions/receipts, fresh reconciliation and a new epoch. Preserve additive tables and all data; no destructive down migration is planned. Mirror failure needs repair/replay, not authority rollback.

## Concrete first implementation step

After the current release SHA is known, create an isolated worktree from that SHA for a **default-off PostgreSQL task transaction slice**. Proposed scope: additive OS workspace/epoch, task, proposal, receipt, event and outbox tables; a new local-only service; transaction integration with synthetic numeric-owner approval; and PostgreSQL integration tests. No live endpoints or settings change, no Google access, no production import or migration, no scheduled mirror worker.

Acceptance tests: same proposal approved concurrently through two channels creates one task/receipt/event/outbox; mismatched request payload/decision/workspace/owner refused; expiry and target change refused; rollback leaves no partial state; lost post-commit response is recovered by exact primary receipt; outbox remains pending without Google; business values/revision and fresh read match the committed transaction. Test actual PostgreSQL rather than treating SQLite/mocked locks as concurrency proof. This bounded slice establishes the atomic core before implementing the full ledger or mirror. It is the next **proposed** implementation task; planning authorization does not authorize its production migration or activation.

Later mirror/recovery acceptance must additionally cover delayed old writes after newer readback with an empty queue, epoch mismatch, restored pending cards, missing receipts across the RPO window and old-primary reconnection. The last supported user-browser observation is still a launcher failure; real-device SLO acceptance needs that access blocker resolved, not an unsupported browser workaround.

## Security/data risks and operating cost assumptions

- Private finances and contacts move into the existing DB failure/security domain. Use dedicated namespaced tables, server-bound workspace filtering and least-privilege roles where practical; no public website/model SQL access. Credentials stay in the existing Secret Manager/runtime boundary. New role/grants or Google access changes require approval. Encrypt backups, restrict restore/export permissions, and log identifiers/reason codes instead of financial/contact payloads.
- Financial risk is semantic drift: floating money, duplicated sources/refunds, date shifts, regenerated identities, partial import and lost approval provenance. Require parity against the actual Script fixtures and import manifest before activation.
- Operational risk is small-VM contention with MIA's existing CRM/owner work. Measure CPU/memory/disk/WAL growth, connection-pool limits and worst-case query/outbox backlog. Bound exporter batches; never hold DB transactions over Google calls. Capacity or managed-DB spending is a later decision.
- Baseline assumption: reuse the already-paid VM and PostgreSQL, so additional fixed compute/DB-service charge is **zero only if capacity suffices**. No extra OS VM, Redis, paid managed DB or model call is needed on the commit path. This is an architecture assumption, not a inspected invoice or quoted production bill.
- Incremental storage/backups/logging/network cost depends on retained DB+WAL/dump volume, region, requests and restore traffic. Calculate `retained GiB × chosen regional rate + operation/egress costs`; [Cloud Storage pricing](https://cloud.google.com/storage/pricing) is usage- and location-dependent. A separate off-host store may incur charges and needs a budget approval; no bucket was created. Existing connector subscription/provider charges and Google quotas must be checked before choosing the mirror adapter.

2. Accept read-only mirror versus a separately approved draft-inbox workflow; choose new mirror workbook or fenced existing workbook, and who may view it.

4. Agree RPO/RTO, backup retention/location/restore-access and spending ceiling; decide whether measured VM capacity is enough or separately approve infrastructure changes.
5. Authorize bounded read-only export/import preparation, resolve migration exceptions and decide old pending/unknown proposal treatment.
6. Approve production additive migration/roles/settings and the exact coordinated backend/Worker contract release, maintenance writer fencing, final import and authority switch only after all gates. This is a distinct approval from the currently authorized 12-file release.
7. Approve limited actual-owner acceptance benchmarks and restore/reverse-migration procedures when concrete and reviewable. No default permission for public leads, outbound messages, broad load tests, credentials or deletion.

The four-second SLO is measured from each action to verified primary state, excluding human approval think time and asynchronous Sheet delivery. Report per-family p50/p95/p99/max, sample sizes, failure/unknown rates and workload/network bounds. Benchmark isolated correctness first, then browser/Worker/VM/DB stages, then approved limited real actions; never pool fast UI controls with writes or sell a percentile as an every-action guarantee.
