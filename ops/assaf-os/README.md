# Assaf OS — shared Google Sheets runtime

This directory contains the Apps Script runtime deployed to the one existing Assaf OS workbook. It does not create a parallel ledger or import the legacy `עסקאות` tabs as income. `LIVE_STATUS.md` distinguishes current deployment evidence from pending owner acceptance.

## Files and deployment order

The bound Apps Script project contains `schema.js`, `core.js`, `runtime.js`, `UnifiedSheets.gs`, `UnifiedRuntime.gs`, and `appsscript.json`. The Advanced Sheets v4 service must be enabled. An operator may call `configureAssafOsBinding(workbookId, workspaceId, ownerId, mode)` to pin the non-secret `TEST` or `LIVE` binding, then run `preflightConfiguredUnifiedWorkbook()` from the Apps Script editor. Installation remains separately gated by the exact `ASSAF_OS_INSTALL_CONFIRMATION` Script Property and `installConfiguredUnifiedWorkbook()`. The explicit-argument `setupUnifiedWorkbook(...)` and `installUnifiedWorkbook(...)` entry points remain available. No code in this repository performs a remote install or deployment, and no secret is accepted by the binding helper.

The installer preserves all unrelated tabs and rows. A legacy two-column `הגדרות` sheet is accepted only when its first two headers are exactly `מפתח`, `ערך`; the installer appends the canonical description/update columns and preserves every existing setting row. Other canonical-name conflicts stop the install before any mutation. If an earlier provider failure left exact-schema empty runtime tabs, preflight reports `partial_installation` with per-tab diagnostics and a manual recovery instruction; it never silently deletes or overwrites them. Five protected hidden sheets hold accepted snapshots, proposals, receipts, replay claims, and sanitized issues. The installer creates one installable `onEdit` trigger for `reconcileAssafOsEdit`.

Required Script Properties (names only; values and secrets never belong in the sheet or logs):

- `ASSAF_OS_OWNER_ID` — one numeric allowlisted owner.
- `ASSAF_OS_WORKSPACE_ID` — exact server workspace binding.
- `ASSAF_OS_WORKBOOK_ID` — exact workbook binding.
- `ASSAF_OS_MODE` — exactly `TEST` or `LIVE`.
- `ASSAF_OS_HMAC_SECRET` — at least 32 characters.

## Signed operations

`doPost` accepts only `{payload,signature}`. Both request and response use a lowercase UTF-8 HMAC-SHA256 signature. The strict signed request contains `api_version`, `operation`, `actor_source`, numeric owner, workspace, workbook, request ID, epoch timestamp, and operation data. It rejects stale timestamps, unexpected keys, wrong bindings, oversized bodies, reused request IDs, and invalid actors. `MIA` may read and propose. Only `OS` or the server's verified `TELEGRAM_APPROVAL` callback context may approve or reject. The model never approves.

Supported operations are `schema`, `snapshot`, `propose`, `proposal`, `approve`, `reject`, and `receipt`. Proposals are immutable, owner-bound, request-idempotent, and expire after ten minutes. Each proposal has stable approval and rejection request UUIDs shared by the browser and Telegram approval paths. Proposal creation writes metadata only. Approval reloads the stored proposal and compares its revision and exact raw/dependency fingerprint, then repeats dependency, refund, currency and source-deduplication validation; replacement values in the approval call are impossible. One Advanced Sheets `batchUpdate` commits field-limited business changes, accepted snapshots, calculated projections, proposal state, replay claim, and receipt. An ambiguous response is recovered with a fresh signed transport request whose `data.request_id` is the original decision ID. Cross-channel repeat approval returns the original receipt and cannot commit twice.

Transport money is integer minor units. Native input cells are readable major units and are converted exactly once. More than two decimal places fails. Refunds require the original received payment, matching person/work/path/currency, a non-earlier date, and a cumulative total no larger than the receipt. The complete original/refund graph is validated again at approval, so changing an original payment cannot invalidate already accepted refunds. Expenses deduplicate the pair `source_type` + `source_key`.

## Native edits and calculations

The edit trigger and snapshot read reconciliation accept complete valid owner input rows, normalize native Google Date cells in the pinned `Asia/Jerusalem` business timezone, allocate stable IDs in memory before semantic validation, increment revisions, and append accepted snapshots. No ID or other system value is written until every row validation passes. Exact header and formula checks run before row mutation. Header changes, formulas, invalid input, duplicate IDs, metadata/system edits, and incomplete rows create sanitized issues and make snapshot coverage partial or unknown. Read reconciliation inspects every row before attempting a projection, while approval, trigger and read paths share the same canonical-input, dependency, refund-graph, expense-dedup and coverage projection gate. One invalid row therefore cannot abort acceptance of an unrelated valid row or refresh financial calculations from invalid data. Unsafe dependent calculated fields are returned as null under partial coverage. Reconciliation writes only system cells that changed. It does not execute proposals or send externally. Each signed request keeps a request-local cache of the fresh raw values and formulas already read from each tab; the cache is discarded before the next request and invalidated after a business write. Stable snapshots skip unchanged projection batches. Native reference validations refresh after an accepted client, work or payment catalog change, or when the current catalog fingerprint differs from the last successful refresh; a failed refresh remains dirty and is retried. After deploying this optimization to an existing workbook, run `refreshAssafOsReferenceValidations` once before the first signed latency probe so the full refresh records its initial fingerprint outside the 15-second port request. If that is not done, the first request performs the refresh itself. This catches additions, edits, removals and repaired duplicate IDs without rewriting the 2,000-row dropdown ranges on every later snapshot.

Native customer and work reference cells use Hebrew dropdown labels that always include the exact stable ID, for example `דנה ⟦PER_...⟧`. Duplicate names therefore remain distinct. Reconciliation extracts the enclosed ID and revalidates an exact existing canonical target; free-text aliases, missing targets and similar-but-different IDs fail closed. API snapshots and proposals continue to use canonical IDs, while OS-written linked cells remain readable. Dropdown choices refresh during workbook reconciliation from versioned customer/work rows. Audit columns (stable IDs, revisions, request/source fields and timestamps) are hidden in the sheet UI but remain available by unhiding them; their schema position and values do not change. Required input cells are shaded pale yellow, and every header has a Hebrew required/optional help note. Expense source keys include a concrete uniqueness example.

Customer and work protected columns are recomputed from receipts and time. All API money, including calculated fields, is integer minor units; native Sheet display cells remain major units. Snapshot coverage is reported overall and per entity. `summary.monthly` is always an array; incomplete payment, expense, work or time coverage produces nullable metrics and reason codes rather than false zeroes. Effective hourly value requires time on every work with non-zero paid cash in that calendar month and currency: known income and recorded minutes remain visible, but the rate is null with `missing_time` when another paid work lacks time. Foreign currencies remain separate. Agreed work values and ad-platform usage reports are excluded from paid cash. Legacy tabs are untouched and excluded from runtime snapshots.

Apps Script locks serialize script writers only. They cannot lock a human editing the workbook. Revision plus raw fingerprint checks detect a conflict, but a simultaneous owner edit can still race with a provider write. Such a conflict requires owner review; the runtime does not silently overwrite or retry.

## Local evidence

Run without Google access:

```powershell
node --test tests/assaf-os/sheet-core.test.js tests/assaf-os/runtime.test.js tests/assaf-os/apps-script-runtime.test.js
```

The VM tests use synthetic rows and Google-shaped mocked Apps Script services. `apps-script-runtime.test.js` loads the actual `.gs` runtime without replacing its operation dispatcher and covers proposal/approval/receipt recovery, cross-channel replay binding, dependent and reciprocal refund integrity, promotion journaling, Jerusalem date boundaries, complete, multi-row and mixed-validity native payment flows, approval-time invalid-finance projection blocking, per-paid-work monthly time evidence across native and MIA/Telegram flows, mixed currencies, canonical native input gates, partial-first-read behavior, formula/header handling, field-limited reconciliation, money conversion, grid bounds, stable-snapshot service-call budgets, change-aware picker refresh, projection drift repair, and schema/snapshot replay-capacity preservation. These tests prove local behavior only. Separately observed Google deployment, real workbook installation, trigger authorization and signed/native checks are recorded in `LIVE_STATUS.md`; live OS and human Telegram acceptance remain pending there.
