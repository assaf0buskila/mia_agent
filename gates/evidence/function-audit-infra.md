# Phase 1.5.3 function audit: capabilities, core, database, integrations, workers, and scripts

Date: 2026-08-28

Scope: read-only cleanup audit of the function-bearing Python files assigned to the infrastructure leaf. This evidence proposes changes; it does not implement any of them.

## Audit method and exact inventory

The inventory was rebuilt from the current worktree by selecting Python files under `app/capabilities`, `app/core`, `app/db`, `app/evals`, `app/integrations`, `app/tools`, `app/workers`, and `scripts` that contain a `def` or `async def`. The result is **68 files**, matching the Phase 1.5 partition. Each file below appears exactly once.

Four passes were completed:

1. **Complete inventory:** opened every assigned file in full and recorded its concrete function/class surface.
2. **Expert reread:** checked each surface against PRODUCT, ARCHITECTURE, accepted ADRs, the Phase 1.5 contract, typed ports, policy boundaries, provider pins, secrets rules, database ownership, deployment safety, and deterministic eval contracts.
3. **Defect/duplication hunt:** traced direct callers and relevant tests, then searched globally for dead symbols, exact duplicates, runtime protocol workarounds, and misleading operator controls.
4. **Free polish:** separated safe cleanup from deliberate repetition and security controls; rejected churn based only on file length or superficial similarity.

Disposition means the recommendation for the file as it exists now. `SIMPLIFY` identifies a bounded change to named symbols; no whole file is recommended for removal or merger.

## Ranked actionable findings

### 1. Release a due-scan notification claim after confirmed send failure

- **File/symbols:** `app/workers/due_scan.py::maybe_notify_due_owner_tasks`, `app/db/store.py::release_owner_notification_claim`.
- **Observed behavior:** due scan inserts the idempotency claim before calling `send_owner_telegram`. A `False` send result returns without releasing the claim. The same-day retry is then rejected as a duplicate.
- **Evidence boundary:** the success/dedupe test exists; no test covers failed delivery followed by retry. Hot handoff already uses the store's release method for the equivalent claim/send failure window.
- **Action:** release only after confirmed non-delivery (including an exception known to occur before delivery), and prove retry plus dedupe behavior mechanically.
- **Risk/benefit:** medium duplicate-send risk if ambiguous outcomes are released; high reliability benefit because a transient provider failure no longer loses the reminder for the day.

### 2. Remove plaintext environment injection from the ECS image-revision script

- **File/symbols:** `scripts/deploy_ecs_revision.py::main`, `_upsert_env`.
- **Observed behavior:** the script describes an image-tag-only revision but accepts repeatable `--env NAME=VALUE` and places values in the task definition's plaintext environment.
- **Action:** delete the option/helper or enforce a small named non-secret allowlist; continue sourcing production secrets only from Secrets Manager.
- **Risk/benefit:** medium compatibility check for legitimate non-secret overrides; high reduction in secret/configuration drift and operator error.

### 3. Pin the ECS migration runner to the migration command

- **File/symbols:** `scripts/run_ecs_migration.py::main`.
- **Observed behavior:** a script documented as schema-only accepts arbitrary `--command`, then runs that command in the production task's network and secret context.
- **Action:** pin the override to `mia-migrate` (or an explicit migration-only allowlist) and add a command-construction test.
- **Risk/benefit:** medium deployment verification cost; high reduction in production blast radius.

### 4. Make the local eval diff cover every deterministic family

- **File/symbols:** `scripts/eval_diff.py::RUNNERS`, `app/evals/harness.py::run_calendar_eval`, `run_routing_eval`.
- **Observed behavior:** both runners exist, are exported, and have unit coverage, but the diff script omits them.
- **Action:** register both without changing scoring or datasets.
- **Risk/benefit:** low; produces a truthful aggregate report and prevents two classes of regression from being silently absent.

### 5. Restore a single async owner-reply port contract

- **File/symbols:** `OwnerReplyPort.compose` and all three implementations in `app/integrations/owner_reply.py`; caller in `app/api/owner.py`.
- **Observed behavior:** the protocol and canned/fake implementations are synchronous, the OpenAI implementation is asynchronous, and the caller compensates using `inspect.isawaitable`.
- **Action:** define one async port, make canned/fake async, directly await at the caller, and retain existing reply/fallback assertions.
- **Risk/benefit:** medium coordinated edit; removes a false typed contract and simplifies the runtime path.

### 6. Delete the exact unused event-count duplicate

- **File/symbols:** `app/db/store.py::count_canonical_events_in_range`.
- **Observed behavior:** its implementation duplicates `count_canonical_events`; global search found no direct caller or test for the `_in_range` name.
- **Action:** remove that method only after a final branch-wide symbol search.
- **Risk/benefit:** low; reduces persistence API ambiguity without splitting the store or touching transactions.

### 7. Remove rejected Sheets name-discovery remnants

- **File/symbols:** `app/integrations/sheets.py::pick_spreadsheet_id`, `_map_spreadsheet_files`.
- **Observed behavior:** neither helper is used by production code; only a unit test imports `pick_spreadsheet_id`. Current owner-sheet behavior uses explicit and allowlisted spreadsheet IDs.
- **Action:** delete the two helpers and obsolete test; update the stale module statement that reads never occur. Do not change allowlists, mirroring, approval, or idempotency.
- **Risk/benefit:** low; eliminates an old discovery model that conflicts with the accepted explicit-ID contract.

### 8. Remove duplicated provider-key fallback expressions

- **File/symbols:** `app/integrations/search_console.py::_map_site_list`, `_map_inspection`.
- **Observed behavior:** fallbacks repeat the same `siteEntry`, `siteUrl`, `inspectionResult`, and `indexStatusResult` lookups on both sides of `or`.
- **Action:** remove the duplicate expressions, or add only provider alternatives demonstrated by fixtures/documentation.
- **Risk/benefit:** low when behavior-preserving; clarifies exactly which response shapes are supported.

- **No architecture churn:** no assigned file merits a whole-file `MERGE` or `REMOVE`. Similar-looking adapters have distinct policy, transport, failure, or provider-shape contracts.
- **Do not split `app/db/store.py` by size:** it is a large aggregate, but a broad split would add transaction/session/migration risk. Only the exact unused duplicate is justified here.
- **Do not split `app/evals/harness.py` by size:** keeping deterministic loaders, scorers, and runners together protects comparable results. Revisit only with a specific eval-family change and full equivalence tests.
- **Do not merge calendar response helpers:** local duplication in `calendar.py` and `calendar_booking.py` avoids coupling/circular-import pressure across read and write paths.
- **Do not create a generic URL helper:** research and SEO audit enforce different allowlists and trust boundaries.
- **Do not merge chat-completion transports:** `sales_reply.py`, `owner_reply.py`, `thread_summary.py`, and `llm_client.py` differ in prompts, async behavior, fallbacks, tools, and deterministic test contracts. The only justified cleanup is the owner-reply port mismatch.

- **Do not remove specified/removed capability entries:** registry and health metadata are product truth, not dead code.
- **Do not auto-add every provider pin to preloaded owner tools:** the preload registry is an authority allowlist, not an inventory of every adapter operation; adding send-capable operations would expand model authority.
- **Do not touch secret, provider, approval, risk, kill-switch, idempotency, tenant, or explicit-resource-ID enforcement as cleanup.** Those are protected contracts, not boilerplate.
- **Do not treat live probes as unit tests:** they intentionally require explicit operator execution and may create real sessions, handoffs, messages, or provider calls.
